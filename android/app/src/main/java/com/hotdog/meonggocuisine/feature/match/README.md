# Match

유사도 분석 요청, 진행 상태, 후보 조회와 후보 비교 상세 기능의 `ui`와 `data` 코드를 둔다.

## 구현 범위

- `data/MatchApi.kt`: M1 매칭 상태·후보 조회와 M2 분석 실행 API
- `data/MatchModels.kt`: M1·M2 응답 DTO
- `data/MatchRepository.kt`: 분석 상태(`AnalysisStatus`), 후보 요약, 비교 모델과 결과 계약
- `data/DefaultMatchRepository.kt`: 오류 코드를 로그인 필요·미존재·권한 거부·일반 실패로 분류
- `ui/MatchProgressScreen.kt`: 분석 시작·처리 중·실패·오래된 결과·조회 불가 화면
- `ui/MatchProgressViewModel.kt`: M2 접수와 상태 폴링
- `ui/MatchProgressUiState.kt`: 진행 화면 단계와 재요청 가능 여부
- `ui/MatchCandidatesScreen.kt`: 후보 목록, 후보 없음, 처리 실패, 조회 불가 화면
- `ui/MatchCandidatesViewModel.kt`: 결과 조회와 재분석 접수
- `ui/MatchCandidatesUiState.kt`: 후보 화면 단계와 오래된 결과 표시 여부
- `ui/MatchComparisonScreen.kt`: 내 반려동물과 후보를 나란히 두는 비교 상세 화면
- `ui/MatchComparisonViewModel.kt`: 기준 게시물과 후보 게시물 상세를 함께 조회
- `ui/MatchComparisonUiState.kt`: 비교 화면 상태와 정성적 추천 근거

## 분석 상태와 화면 단계

M1의 `analysisStatus` 하나로 화면 단계가 갈린다.

| `analysisStatus` | 화면 단계 |
| --- | --- |
| `NOT_REQUESTED` | 분석 시작 안내와 `유사도 분석하기` |
| `PENDING`, `RUNNING` | 처리 중 |
| `SUCCEEDED` | 후보 화면으로 이동 |
| `FAILED` | 처리 실패 — 후보 없음과 구분해 표시 |
| `STALE` | 게시물이 바뀜 — 이전 후보를 보존하고 자동 분석하지 않음 |

`STALE`이 새 실행의 처리 중 상태와 겹치면 서버는 `analysisStatus=STALE`을 유지하고 실제 최신
상태는 `latestRun.status`에 담는다. 그래서 폴링 판단은 `analysisStatus`가 아니라
`latestRun.status`를 따르고, 처리 중이면 처리 중 단계를 먼저 표시한다.

## 폴링 규칙

- 조회 간격은 서버가 준 `recommendedPollAfterMs`를 사용한다. 값이 없을 때만 기본값을 쓴다.
- 화면이 보이는 동안에만 조회한다. `LifecycleStartEffect`로 시작·중단해 백그라운드에서 조회하지 않는다.
- 처리 중이 아니면 반복을 멈춘다.
- 권한·상태 거부(`AUTH-002`, `POST-001`, `POST-002`, `POST-003`, `MATCH-001`)를 받으면 폴링을
  멈추고 기존 분석 상태·후보 표시를 제거한다.
- 조회 자체가 실패한 경우는 분석 실패와 구분한다. 서버에는 실행이 남아 있으므로 이미 알고 있는
  단계를 유지한 채 오류만 알린다.

## 화면 규칙

- 본인의 활성 `잃어버렸어요` 게시물 상세에서만 진입한다. 진입 조건은 게시물 상세가 판단하고,
  서버도 매 요청마다 작성자 권한을 검증한다.
- 서버가 진행률을 주지 않으므로 수치형 진행률을 표시하지 않는다.
- 신규 입소 자동 감시·재비교·푸시 알림 문구는 표시하지 않는다. MVP 이후 범위다.
- 원시 점수, 백분율, 정확한 거리는 화면 모델에 담지 않는다.

## 기준 게시물 요약

후보 화면 상단의 내 신고 요약에는 사진, 이름, 품종·성별·색상, 공개 지역, 실종 일시가 필요하다.
M1은 기준 게시물의 `postId`만 내려주므로 이 기능의 `MatchApi`에서 게시물 상세를 따로 조회하고
필요한 필드만 담은 DTO를 둔다. `feature/post`를 직접 참조하지 않기 위한 선택이며, 요약 조회가
실패해도 후보 표시는 막지 않는다.

## 후보 화면 규칙

- 후보는 서버가 정한 `rank` 순으로 표시한다. 임계값과 상위 20건 제한은 서버가 적용한다.
- 카드에는 사진, 이름 또는 품종, 동물 정보, 공개 지역, 사건 날짜, 출처를 표시한다.
- 사용자 후보는 작성자 닉네임을, 공공 후보는 보호소 이름과 공식 전화번호를 표시한다. 회원 개인
  연락처는 표시하지 않는다.
- 공공 후보의 `CLOSED`는 현재 보호 중이 아닌 과거 소급 후보이므로 `과거 기록` 배지로 알린다.
- 유사도 백분율, 원시 점수, 정확한 거리는 화면 모델에 담지 않는다. M1이 응답하지 않는 값이며
  사용자에게 표시하지 않는다. Figma 시안의 `유사도 92%`와 `4.2km` 자리에는 M1이 공개하는
  `rank`를 `닮은 순서 N위`로 표시한다.
- 후보는 3칸 격자로 보여 주고, 처음에는 6건까지만 표시한 뒤 `더 많은 결과 보기`로 나머지를
  펼친다. 최대 20건이라 lazy 목록을 쓰지 않는다.
- 정렬은 서버가 정한 `rank` 순으로 고정이다. 정렬 변경 파라미터가 없으므로 정렬 선택 UI를 두지
  않고 현재 기준만 표시한다.
- 후보 없음은 처리 실패와 다른 화면으로 표시하고, 재분석·게시물 수정·목록 복귀 동선을 제공한다.
- 최신 실행이 실패했거나 처리 중이어도 보존된 이전 성공 결과가 있으면 후보를 보여 주고, 그
  사실을 안내로 알린다.

## 진행 화면과 후보 화면의 경계

진행 화면은 처리 중 상태를 폴링으로 따라가고, 후보 화면은 끝난 결과만 보여 준다. 그래서 후보
화면이 조회한 상태가 아직 처리 중이면 폴링을 시작하지 않고 진행 화면으로 돌려보낸다. 후보
화면의 `다시 분석하기`도 M2를 접수한 뒤 진행 화면으로 이동한다.

## 비교 상세 규칙

후보 카드를 선택하면 내 반려동물과 후보를 같은 항목으로 나란히 비교한다.

- M1은 후보의 `postId`만 내려주므로 두 게시물 상세(P2)를 각각 조회해 한 화면에 합친다. 기준
  게시물 요약과 같은 이유로 `feature/post`를 참조하지 않고 이 기능의 좁은 DTO를 쓴다.
- 두 조회 중 하나라도 실패하면 비교를 보여 주지 않고 오류와 다시 시도만 제공한다. 한쪽만 있는
  비교는 오해를 만든다.
- 후보 이름이 없는 공공 동물은 `보호소 #공고번호`로 표시한다.
- 유사도 백분율과 정확한 거리는 표시하지 않는다. 추천 근거는 임계값을 통과한 후보라는 사실,
  사건 시점 관계, 공개 지역만 담는다. Figma 시안의 `실종 장소에서 4.2km 거리예요` 자리에는
  후보가 실종 이후에 발견되었다는 시점 근거를 표시한다.
- 같은 아이로 확정된 결과가 아니라는 안내를 항상 함께 표시한다.
- 연락 동선은 출처가 정한다. 공공 후보는 보호소 공식 전화, 사용자 후보는 `chat.available`이
  참일 때만 작성자와의 채팅으로 이어진다. 불가한 경우 이유를 안내로 표시한다.
