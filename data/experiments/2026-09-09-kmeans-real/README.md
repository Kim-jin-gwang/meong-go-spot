# 실벡터 K-Means 색인 실험 (2026-09-09, #109)

45만 장 실제 임베딩(DINOv2 ViT-B/14 v2, 768차원)으로 MapReduce K-Means 색인을 처음 만들고, **색인으로 후보를 줄였을 때
정확 탐색 대비 recall 을 얼마나 잃는지**를 -108 평가 하네스의 같은 2만 쌍으로 측정했다. 지금까지 K-Means 는 합성 벡터
(2M×128d, 13k×64d)로만 실측했고 실데이터 분포·시간은 미지였다.

## 설정

| 항목 | 값 |
|---|---|
| 입력 | `/embeddings/dinov2_vitb14/v2/shelter-backfill/yyyymm=*/vectors-*.tsv` — 261 파일, 3.1GB, **452,486 벡터**(백필 452,470 + 재시도 회복 16) × 768 |
| 초기화 | `InitCenters` k-means++, 저수지 표본 100,000, seed 42, `-Dmungo.vector.meta=…/_meta.json` |
| 반복 | `KMeansDriver` 최대 10회, ε=1e-3(미도달 — 10회 상한 종료), Combiner on, `CombineTextInputFormat` 128MB → **맵 24개**/잡 |
| 클러스터 | YARN 2노드 6 vCores(4096+6144MB), 서버 2 클라이언트 |
| 평가 | `eval_recall.py --assignments --centers --nprobe 1 2 4 8 16 32`, 쌍 20,000(seed 42, 중복 제외), 갤러리 452,470(-108 로컬 사본) |
| 산출 | `/embeddings/dinov2_vitb14/v2/index/kmeans-k256/{centers.tsv, work/assignments/}` |

## 실행 시간 (`kmeans-metrics.json`, 잡 카운터)

| 단계 | 소요 | 비고 |
|---|---|---|
| InitCenters | **91초** | HDFS 읽기 49초(45만 줄 전량 스캔) + k-means++ 39초(표본 10만) |
| K-Means 반복 ×10 | **1,426초** (반복당 125~140초) | 잡당 CPU 546초 = 6 vCores 거의 풀가동 → CPU 바운드. Combiner 가 맵 출력 452,486 → 11,821건(−97%), 셔플 145MB/반복 |
| 배정(맵 전용) | ~100초 | 출력 24 part, 452,486 줄 |
| **전체** | **1,517초 = 25.3분** | 22:30 일일 파이프라인과 겹치지 않게 낮에 실행 |

중심 이동량(L2² 합): 82.75 → 2.84 → 1.07 → 0.59 → 0.41 → 0.25 → 0.16 → 0.11 → 0.085 → 0.070. 3회부터 완만한 감소 —
운영 재구축은 **5회면 충분**(이동량 0.4 이하, 이후 recall 차이는 측정 오차 수준일 것; 별도 확인은 후속).

스케일 실험(2M×128d, k=50)의 247초/2반복 대비, 레코드당 거리 계산이 30배(256×768 vs 50×128)라 반복당 7배 무거운 예상이
실측 130초로 들어맞았다(레코드 수는 4.4배 적음).

- **nprobe=16 이면 후보를 1/14 로 줄이고도 recall 손실이 0.001 이내.** nprobe=8 은 1/27 에 R@20 −0.008. nprobe=4 부터 손실이 보인다(−0.027).
- "정답이 범위 밖" 7.9%(nprobe=16)인데 recall 이 그대로인 이유: 범위 밖으로 밀린 정답은 정확 탐색에서도 이미 20위 밖이던 어려운 쌍(한쪽 폴백 등)이다. 색인은 **맞힐 수 있던 쌍은 거의 잃지 않는다.**
- 평가 시간이 nprobe 에 따라 느는 건 채점기가 정확 점수도 함께 계산하는 구현 탓이고, 실제 소비자는 후보만 계산한다.

## 결론·운영 값

1. **대안 B(상주 서비스) 색인 방식이 성립한다**: 질의당 중심 256개와 내적 → 가까운 16개 클러스터의 사진(~32,000장)만 비교. 정확 탐색 45만 내적 대비 14배 적은 계산에 recall 동일.
2. **권장 기본값: k=256, nprobe=16.** 지연이 더 급하면 nprobe=8(손실 0.008), 정확도 우선이면 32(손실 0).
3. k=1024 는 만들지 않았다 — 256 에서 이미 손실이 0 이라 더 잘게 나눌 이유가 없고, 반복당 4배 비용이다. 갤러리가 수백만으로 커질 때 재검토.
4. 색인 재구축은 25분(5회 반복이면 ~13분). 일일 증분은 재구축 없이 기존 중심으로 배정만 한다 — 2026-09-10 부터 `index_tools.py assign` 이 DAG 5번째 태스크로 자동 수행한다(실측 937~1,537장에 22초). 재임베딩(모델 교체) 때만 전체 재구축.
5. ~~갤러리 452,470 vs 배정 452,486 의 차이 16~~ → 2026-09-10 해소. 로컬 TSV 사본을 갱신하는 대신 평가가 **이진 스냅샷**을 읽게 했다(`eval_recall.py --snapshot`, 로딩 65초 → 0.5초). 스냅샷은 매일 파이프라인이 다시 쓰므로 일일 증분까지 자동으로 들어오고, 사본을 따로 유지할 필요가 없다.

## 추가 측정 — 배치에서 파싱이 차지하는 몫 (2026-09-10)

"TSV 파싱이 배치도 느리게 하는가"를 답하려고 **k=1과 k=256을 각각 1반복** 돌려 CPU를 비교했다.
중심이 1개면 거리 계산이 사실상 사라지므로, 두 실행의 차이가 곧 거리 계산 몫이다. 입력·경로·설정은 동일.

| 항목 | k=1 | k=256 | 차이 |
|---|---|---|---|
| 1반복 CPU | 269초 | 520초 | **251초** |
| 1반복 wall | 82초 | 183초 | 101초 |
| Combine 출력 레코드 | 47 | 11,919 | |
| 셔플 | 0.7MB | 149MB | |

**해석 주의 (2026-09-10 정정)**: 251초 차이를 전부 거리 계산으로 볼 수 없다. k를 키우면 거리 계산 외에도
컴바이너 출력이 47건 → 11,919건(253배), 셔플이 0.7MB → 149MB(213배)로 함께 늘고 리듀서 입력도 그만큼 늘어난다.
따라서 **251초는 거리 계산 몫의 상한**이고, 실제 거리 계산은 그보다 작다. 반대로 **파싱·직렬화 몫은 269초보다 크다.**

확실히 말할 수 있는 것만 적으면 이렇다.

- 반복당 CPU 520초 중 **최소 269초(52%)가 거리 계산이 아닌 일** — 파싱·직렬화·프레임워크다.
- 그 안에 **같은 벡터를 두 번 파싱하는 일**이 있다: 매퍼가 입력 TSV를 파싱하고, 컴바이너가 매퍼 출력
  (`건수|벡터텍스트`)을 **다시** 파싱한다. 리듀서도 파싱하지만 컴바이너를 지난 11,919건뿐이라 작다.
- 거리 계산과 셔플 증가분을 갈라내려면 **k를 고정하고 형식만 바꿔** 비교해야 한다. 이번 설계로는 안 된다.

**결론: 지금 이진으로 바꾸지 않는다 — 다만 근거는 "값어치가 낮다"가 아니라 "우선순위가 낮다"다.**

- 입력을 SequenceFile로 바꾸면 파싱 하나가 없어져 반복당 CPU를 최대 25% 줄인다. 25분 작업이 20분쯤 된다.
  대가는 컨버터 잡 추가, 드라이버 3종의 입력 형식 변경, `hdfs dfs -cat`으로 눈으로 확인할 수 없게 되는 것,
  그리고 다른 소비자를 위해 TSV를 어차피 유지해야 하는 것이다.
- 더 싼 대안이 있다: **매퍼 출력 형식만** 이진으로 바꾸면 컴바이너 재파싱이 사라진다. 입력 계약은 그대로이고
  잡 내부 변경이라 영향 범위가 작다. 절감 폭은 비슷하다.
- 둘 다 하지 않는 이유는 **아픈 곳이 아니기 때문**이다. 배치는 재임베딩할 때만 도는 25분이고, 실제로 아팠던
  서빙 로딩 65초는 이진 스냅샷으로 해결했다(0.5초). 배치가 일상 병목이 되면 **먼저 k를 고정한 형식 비교로
  다시 측정한 뒤** 판단한다 — 이번 측정은 그 판단의 근거가 되기에 부족하다.
