# 분실동물 공공 API(lossInfoService) 조사 (2026-09-15, #145)

'잃어버렸어요' 탭에 공공 분실동물을 넣기 위해 `lossInfoService/lossInfo` 를 전량 받아 본 기록이다.
적재 설계(-145)와 그 선행 조건인 BE 설계에 필요한 사실만 적는다. 원문은 저장하지 않았다 — 신고자 이름·전화번호가
들어 있어 레포에 두지 않는다.

## 호출

`https://apis.data.go.kr/1543061/lossInfoService/lossInfo` — `serviceKey`·`numOfRows`·`pageNo`·`_type=json`. 기간·지역 파라미터 없음.
**`totalCount` 는 믿을 수 없다** — 303 이라고 하는데 실제 페이지는 100 + 63 + 빈 페이지 = **163건**(2026-09-13 에는 308 이라 하고 172건).
빈 페이지가 나올 때까지 돌아야 한다. `data/collector/api.py` 의 `fetch_lost_all` 이 그렇게 한다.

## 필드 (14개, 2026-09-15 전량 163건)

| 필드 | 채움 | 뜻 · 관찰 |
|---|---|---|
| `happenDt` | 100% | 실종 일시 `2026-09-14 13:00:00.0` — 초 단위. 보호동물 API 의 `YYYYMMDD` 와 형식이 다르다 |
| `happenAddr` / `happenAddrDtl` / `happenPlace` | 100% / 일부 / 100% | 도로명 주소 + 상세 + 자유 지명. **주소가 있어** 지역 코드 해석은 `happenAddr` 로 하면 된다(보호동물처럼 orgNm 캐스케이드 불필요) |
| `orgNm` | 100% | 관할 기관("서울특별시", "전남광주통합…") — 뒤에 공백이 붙어 온다 |
| `kindCd` | 99% | **품종 이름**("믹스견", "코리안 숏헤어", "푸들"). `upKindCd`(축종 코드)가 **없다** — 축종을 품종 이름에서 유도해야 한다 |
| `colorCd` / `sexCd` / `age` / `specialMark` | 대부분 | 색·성별(M/F)·나이("2살")·특징 |
| `popfile` | **100%** | 사진 1장, `http://` (보호동물과 같은 파일 서버 — `_https` 정규화 그대로) |
| `rfidCd` | **29%** (48/163) | 마이크로칩 번호 — 있으면 개체 식별자로 쓸 수 있다 |
| `callName` / `callTel` | 89% 실명·실번호, **11% "신고자 요청으로 표출되지 않습니다"** | **신고자(비회원) 개인정보** |
| 없는 것 | — | **고유 ID 없음, 상태 없음, `updTm` 없음** |

## 축종 유도 — 품종 이름 → 개/고양이

보호동물 API 의 품종 사전(`abandonmentPublicService_v2/kind_v2`, `up_kind_cd` 417000/422400 → 개 203·고양이 37, "기타" 제외)으로 매핑했다.
규칙(`data/collector/breed_species.py`): 정확 일치 → 사전 이름이 입력을 **포함**하는 것들의 축종이 하나면 그 축종("푸들" ⊂ "토이 푸들" → 개)
→ "기타"·"기타축종" 은 OTHER → 그 밖은 미확정. 사전은 `infra/reference/breed-species.csv`(`data/reference/build_breed_species.py` 가 생성).

| 결과 (2026-09-15 실데이터 163건) | 건수 |
|---|---|
| 개 | 110 |
| 고양이 | 26 |
| **"기타"·"기타축종" → OTHER, 축종 미상** | **25 (15%)** |
| 빈 값 → 미확정 | 2 |

**"기타" 가 문제다.** 개 사전과 고양이 사전 양쪽에 "기타" 가 있어 이름만으로는 개인지 고양이인지 알 수 없다(처음엔 사전 순서 때문에
18건이 고양이로 잡혔는데 근거가 없는 배정이었다). 15% 를 버리지 않으려면 `specialMark`·`colorCd` 같은 자유 텍스트에서 추측해야 하는데,
그것은 적재기가 할 일이 아니다 — **`kindCd` 가 "기타" 인 건은 적재에서 빼고 실패 사유(`SPECIES_UNRESOLVED`)로 남긴다**. 포털에
`upKindCd` 를 요청하는 것이 정석이다.

## 멱등 키

고유 ID 가 없다. 후보 키 `sha256(happenDt + happenAddr + popfile)` 은 163건에서 **중복 0**. `rfidCd` 가 있으면 그것이 더 좋은 키지만
29% 만 있다. 사진이 교체되면 새 건으로 들어오는 한계는 이슈 본문대로 문서화한다. 상태·`updTm` 이 없으므로 **매일 전량을 받아 사라진 건을 CLOSED 로 내린다**(2페이지라 가능).

## 용량

사진 1장 ≈ 120KB × 163 ≈ 20MB. 표시는 공공 URL(이미지 캐시 프록시 `/img/loss/…` 가 이미 경로를 허용한다)로 하고 HDFS 에 보존하지 않는다. **HDFS 영향 0.**

## 선행 조건 — 이것이 없으면 적재할 수 없다

1. **DB 제약 `ck_animal_case_source_type_pair`** (`PUBLIC` 은 `SHELTERING` 만) 와 `docs/erd.md` 규칙 1, `docs/api-spec.md:210` "PUBLIC은 항상 SHELTERING이다" 를 푸는 **BE 설계·V3 마이그레이션·목록/상세 노출**. 2026-09-15 현재 **Jira 에 이 BE 이슈가 없다** — 만들어져야 -145 가 끝날 수 있다.
2. **신고자 연락처 정책 (제품·BE 결정)**: 89% 가 비회원의 실명·전화번호다. 우리 정책은 회원 연락처를 어떤 응답에도 넣지 않고(`api-spec.md:628`) 개인정보는 암호화 저장한다(`backend-security-operations-policy.md`). 공공 포털은 그대로 공개하지만, 우리가 **저장·표시할지 / 암호화해 상세에서만 보여줄지 / 저장하지 않고 "포털에서 확인" 링크만 둘지**는 DATA 가 정할 일이 아니다. 결정 전까지 적재기는 `callName`·`callTel` 을 **버린다**(마스킹 문구 포함).
3. 축종 미상 27건(17%, "기타" 25 + 빈 값 2)은 제외한다. 줄이려면 포털에 `upKindCd` 제공을 요청해야 한다.
