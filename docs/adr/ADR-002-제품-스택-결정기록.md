## D1. 빅데이터 클러스터 실행 환경 — ✅ 확정: (b′) 서버 2대 멀티노드 (2026-08-26)

**선택지:**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| (a) 단일 서버 + Docker 의사분산 | 서버 1대에 Hadoop/Kafka 컨테이너, 다중 워커 프로세스 | 관리 단순 | 물리 분산 아님 — 서버 2대면 아까움 |
| **(b′) 발급 서버 2대 멀티노드** | 서버1 = 서비스(API·DB·Jenkins) + 워커 겸용, 서버2 = 클러스터 마스터(NameNode·RM) + 워커. HDFS 복제 계수 2 | **진짜 물리 분산 시연** + 상시 가동이라 안정 (PC 연합과 다름) | 2노드 구성·네트워크 설정 비용, 서버1의 서비스↔워커 자원 경합 관리 필요 |

**추천: (b′)** — 당초 (b)의 단점은 "팀원 PC라서 불안정"이었는데, **발급 서버 2대는 상시 가동이라 그 단점이 사라진다.** 물리 분산을 실제로 시연할 수 있어 과제 서사에도 가장 강하다. 서버가 1대만 나오는 경우의 폴백이 (a).

## D2. 스트리밍 — ✅ 사실상 확정

**Kafka.** 과제 요구 스택이며 람다 아키텍처의 실시간 축. 토픽 설계(수집분/입소 이벤트 분리)는 구현 이슈에서.

## D3. 배치 프레임워크 — ✅ 사실상 확정

**순수 Hadoop MapReduce로 5종 알고리즘 직접 구현.** Spark가 생산성은 높지만, 이 과제는 kNN 조인·행렬곱·쎄타조인·자카드·K-Means를 MapReduce로 구현하는 것 *자체가 목적*. Spark는 성능 비교 대조군으로만 언급 (여력 있을 때).

## D4. 임베딩 모델 — ✅ 확정: YOLO26l-seg + DINOv2 ViT-B/14 2단 파이프라인 (2026-09-03 · 주도: **AI 담당**)

**당시 후보 비교 (결정 근거로 보존):**

| | CLIP (ViT-B/32) | DINOv2 |
|---|---|---|
| 특성 | 멀티모달(이미지-텍스트) | 시각 전용, 세밀한 시각 특징 |
| 강점 | 속성 텍스트 결합("갈색 푸들") 활용 여지 | 개체 구분(같은 품종 내) 우위 가능성 |
| 차원 | 512 (설계 기준과 일치) | 384~1024 (모델 크기별) |

**추천: 결정을 미루고 1주차 스파이크에서 실데이터(보호소 사진 ~1만 장) recall로 비교.** 벤치마크(Petco Love Lost)가 증명한 건 "사진 매칭이 된다"는 것이지 특정 모델이 아님. 철창·저화질 환경에서의 실측이 유일한 근거.

**확정 결과 (2026-09-03): YOLO26l-seg → DINOv2 ViT-B/14 2단 파이프라인.**

- **YOLO26l-seg**: 사진에서 개·고양이 개체를 탐지하고 마스킹·크롭하는 전처리 단계
- **DINOv2 ViT-B/14**: 크롭 이미지 → 768차원 임베딩 벡터. **frozen 백본 그대로 사용, 파인튜닝 없음**
- 근거: 1주차 D4 스파이크에서 frozen DINOv2 백본만으로 재식별 **Top-1 97.3%** 확인
- **CLIP 기각**: 같은 스파이크에서 DINOv2가 개체 재식별 성능 우위 — 매칭 본체가 요구하는 것은 개체 구분이므로 DINOv2 채택
- 세그멘테이션 모델(YOLO26l-seg)과 마스크·크롭 규격도 **전처리 스펙의 일부** — 변경 시 `model_version`을 올리는 대상에 포함 (D5의 버전 불일치 경고와 동일 원칙, [data-ai-interface.md](../data-ai-interface.md) §4)
- DINOv2 구체 모델은 **ViT-B/14**, 임베딩 차원은 **768**로 확정 ([data-ai-interface.md](../data-ai-interface.md) §3)

## D5. 임베딩 서빙 방식 — ✅ 확정: (b) 온디맨드 Python 서비스 (2026-08-26 · 주도: **DATA 담당** · 모델 규격은 AI 담당 제공)

**선택지:** (a) 배치 잡에서만 임베딩 생성 (증분 매칭도 미니 배치로) / (b) 경량 Python 서비스(FastAPI)로 온디맨드 임베딩 — 신규 신고 즉시 매칭에 필요

**추천: (b)** — "분실 신고 등록 → 곧바로 후보 확인" UX가 핵심 시나리오라서, 신고 시점 임베딩은 온디맨드가 필요. 단 배치 파이프라인과 동일 모델·전처리를 공유할 것 (버전 불일치가 매칭 품질을 조용히 깨는 고전적 사고). **역할 분담**: 파이프라인·서빙 구조는 DATA가 소유하고, 모델 선택·전처리 규격(D4 결과)은 AI가 제공한다 — 경계는 "모델 아티팩트 + 전처리 스펙" 인터페이스.

## D6. 매칭 결과 전달 — ✅ 확정: (a′) 클러스터 색인 + 직접 계산 (2026-08-26 · 주도: DATA · BE 협의)

**확정된 요구사항: 신고 직후 첫 후보가 즉시(수 초 내) 나와야 한다.** 이에 따라 실시간 경로와 배치 경로를 다음처럼 나눈다:

**신고 순간의 실시간 경로 — 미리 계산할 수 없는 부분**

```text
사진 업로드 → 임베딩 생성 (D5 온디맨드, <1s)
           → 배치가 만든 K-Means 클러스터 중심(수백 개)과 비교 → 가까운 그룹 2~3개 선택
           → 그 그룹의 후보(수천~수만)만 정밀 비교 → Top-20 즉시 응답
```

전체 수백만과 비교하는 대신 **MapReduce가 미리 만들어 둔 클러스터를 색인으로 사용** — 실시간 검색조차 배치 산출물 위에서 돈다 (과제 정체성 유지).

**MapReduce 배치가 미리 계산하는 것 (실시간이 아닌 것)**

| 사전 계산물 | 역할 |
|---|---|
| K-Means 클러스터 + 중심 벡터 | 위 실시간 경로의 색인 (1×수백만 → 1×수만) |
| 기존 활성 신고 × 신규 입소 kNN 조인 | 신고 후 **지속 감시** — 닮은 동물이 새로 입소하면 푸시 (서비스 차별점) |
| 동물×동물 유사도(행렬곱)·자카드 | 재식별, 입양 추천 — 순수 배치 기능 |

**기각: (b) pgvector 즉석 검색** — 즉시성은 같지만 실시간 매칭 경로가 과제 스택 밖(DB 인덱스)이 됨. 단, **폴백 조건 명시**: 스파이크에서 (a′)의 응답 시간이 목표(수 초)를 못 맞추면 (b)를 실시간 보조 경로로 재검토.

## D7. 푸시 알림 — ✅ 제한 적용: 일일 입소 요약 (2026-09-01 D9로 갱신)

FCM은 일일 보호센터 증분 적재의 신규 입소 건수 요약에만 사용한다. 알림을 허용하고 `daily-intake-summary` 토픽을 구독한 기기에 하루 한 번 발송하며, 앱 내에서도 같은 요약을 확인할 수 있게 한다. 개별 유사 후보·자동 재분석·채팅에 대한 푸시는 MVP에서 제공하지 않는다.

## D8. 데이터베이스 — ✅ 확정 (ADR-001 D3 승계)

**PostgreSQL 17.** 서비스 데이터와 배치 결과 적재를 위한 DB다. 개발용 Docker Compose 환경과 Flyway V1의 13개 테이블이 구축됐다(MR !78). Hibernate는 `validate`를 사용한다. 도메인 엔티티·API 구현과 운영 적용 검증은 후속 작업이다.

## D9. MVP 분석·알림 흐름 — ✅ 확정 (2026-09-01)

`잃어버렸어요` 게시물의 등록·수정, 보호센터 데이터 적재와 스케줄은 사용자별 유사도 분석을 실행하지 않는다. 본인 활성 게시물 상세에서 사용자가 `유사도 분석하기`를 선택했을 때만 요청 시점의 검색 대상에 대해 분석을 시작한다.

MapReduce 구현은 최종 후보와 Top-K 계산 규칙의 본체다. 임베딩 생성, 색인·클러스터 준비와 공공 데이터 증분 적재는 사전에 수행할 수 있지만, 이 준비 작업만으로 사용자별 후보 결과를 생성하거나 알리지 않는다. M2는 `match_run(PENDING)`을 202로 접수하고 DATA/AI worker가 선점해 결과를 적재한다. YARN 잡 기동 오버헤드 때문에 M2마다 새 잡을 실행하지 않는다. 초기 SLO는 접수 p95 500ms, 결과 1~3장 p95 10초·10장 p95 30초, hard timeout 60초이며 부하 시험으로 갱신한다.

일일 보호센터 증분 적재가 성공하면 신규 보호동물 수와 보호소 수를 알림을 허용하고 `daily-intake-summary` 토픽을 구독한 기기에 푸시로 한 번 요약한다. 모든 사용자는 앱 내에서도 같은 요약을 확인할 수 있다. 개별 유사 후보 알림·자동 재분석·채팅 푸시는 MVP 범위에서 제외한다.

## D10. 채팅 상태·알림·갱신 — ✅ 확정 (2026-09-17)

채팅 목록에서 안 읽은 대화를 구분하고 여러 화면 진입 경로에서 동일한 상태를 복원하기 위해,
고정 1:1 방의 참여자별 마지막 읽음 메시지 ID를 기존 `chat_room`의 작성자·요청자 컬럼에 저장한다.
메시지마다 읽음 행을 만들지 않고 명시적인 C5 요청으로 같은 방의 현재 위치보다 앞으로만 이동한다.
메시지 GET과 FCM 수신은 읽음 상태를 바꾸지 않는다.

상대방의 앱 연결 여부와 무관하게 메시지 저장을 보장하기 위해 PostgreSQL commit을 전달의 최종
기준으로 삼는다. 새 메시지와 수신자 한 명의 `CHAT_MESSAGE` Outbox 이벤트를 같은 트랜잭션에
저장하고, 별도 worker가 현재 회원의 활성 인증 세션에 등록된 기기로 본문 없는 FCM data 메시지를 보낸다. FCM
실패는 메시지를 롤백하지 않으며 일시 실패는 재시도하고 영구 토큰 오류는 기기 등록을 제거한다.
개인 기기는 설치 UUID로 등록하며 토큰은 목적별 암호화·조회 HMAC으로 보호한다. 일일 입소 요약
토픽과 개인 채팅 기기 등록은 서로 분리한다.

대화 화면 갱신은 `afterMessageId` REST 증분 조회를 약 3초마다 사용한다. WebSocket·SSE는 MVP에
도입하지 않는다. 알림은 화면 진입 힌트이고 C2·C3 DB 조회가 누락 복구 경로다. 이 결정은 D7·D9의
개별 유사 후보 알림 제외를 바꾸지 않으며, 두 항목의 채팅 푸시 제외 문장만 대체한다.
