## 1. 요약

1. **현행 v2(l_b)는 5장부터 NFR 5초를 초과한다** (5장 5.2초, 10장 10.5초). 병목은 탐지(YOLO26l-seg) — 10장 기준 전체의 70%.
2. **RAM은 전혀 병목이 아니다** — 모든 측정에서 시스템 여유 메모리 최소 10.1GB 유지 (프로세스 피크 RSS 최대 1.2GB).
3. **사이즈를 낮추면 NFR 안에 들어온다**: `s_s` 10장 3.3초, `n_s` 2.0초. 단, **탐지 성공률이 떨어진다** (l 20/30 → s 18/30 → n 16/30) — 폴백은 원본 전체 임베딩이라 매칭 품질 저하로 이어진다.
4. **권고: `s_s`(YOLO26s-seg + vits14)** — 10장 3.3초로 NFR 충족, 탐지 손실 최소(l 대비 −2장), 임베딩 겹침 비교에서 s_b(0.96)보다 낮지만(0.71) vits14 전환의 영향이며 별도 재식별 정확도 검증 후 확정. 보수적 대안은 `s_b`(10장 5.6초, 8장까지 충족).
5. UX 판정: 부하 테스트 결과 참조 (§5).

같은 30장, 장수별 p50 (초). RSS 는 프로세스 피크.

| 조합 | 1장 | 5장 | 10장 | 10장 YOLO | 10장 DINOv2 | 피크 RSS | NFR 충족 장수 |

| `l_b` (현행 v2) | 1.18 | 5.23 | 10.55 | 7.39 | 3.02 | 1.1GB | ~4장 |
| `s_b` | 1.54* | 2.85 | 5.63 | 2.23 | 3.18 | 1.0GB | ~8장 |
| `n_b` | 0.48 | — | 4.63 | — | — | 1.1GB | 10장 |
| `l_s` | 0.86 | — | 8.70 | — | — | 0.8GB | ~5장 |

\* s_b 1장 값은 첫 측정 워밍업 잔향으로 2장(1.31초)보다 크게 나옴 — 장당 기울기(~0.55초)로 보는 것이 맞다.

### 품질 대리 지표

**탐지 성공률** (30장, 비폴백 수 — 폴백은 배경 제거 없이 원본 전체를 임베딩):

| 탐지 모델 | 성공 | confidence 평균 |
|---|---:|---:|
| YOLO26l-seg (현행) | 20/30 | 0.888 |
| YOLO26s-seg | 18/30 | 0.882 |
| YOLO26n-seg | 16/30 | 0.847 |

**임베딩 순위 보존율** — 30장 임베딩의 이미지별 Top-5 이웃(코사인) 집합을 현행 `l_b`와 Jaccard 비교:

| 비교 | 평균 겹침 |
|---|---:|
| `s_b` (탐지만 s) | 0.962 |
| `n_b` (탐지만 n) | 0.848 |
| `l_s` (임베딩만 vits14) | 0.712 |
| `s_s` | 0.712 |
| `n_s` | 0.676 |

- 탐지를 s로 낮추는 것은 순위를 거의 바꾸지 않는다(0.96). n은 폴백 증가(+4장)로 겹침이 더 떨어진다(0.85).
- **vits14 전환은 이웃 구성을 뚜렷이 바꾼다**(~0.71). 나쁘다는 뜻이 아니라 *다르다*는 뜻이다 — 재식별 정확도(Top-1/margin)는 라벨 있는 데이터셋으로 별도 검증해야 하며, 30장 Jaccard 는 표본이 작아 참고치다.

### 사이즈 적정성 판정

- **YOLO26l-seg 는 CPU 서빙에 과하다.** l→s 로 탐지 시간이 1/3.3(10장 7.4→2.2초)이 되는데 탐지 손실은 2장, 순위 보존 0.96. **탐지는 s 권고.** n 은 속도 이득 대비 탐지 손실(−4장)이 커서 비권고.
- **vitb14→vits14 는 속도 3.1배**(10장 3.0→1.0초)지만 순위 변화가 커서, **재식별 정확도 검증(별도 이슈) 통과를 조건으로 권고.** 검증 전 보수안은 `s_b`.

## 4. 콜드 스타트·RAM

| 조합 | 탐지기 로드 | 임베더 로드 | 피크 RSS |
|---|---:|---:|---:|
| `l_b` | 0.5초 | 2.0~3.7초 | 1.1GB |
| `s_s` | 0.4초 | 1.0초 | 0.6GB |

- 작업 중 시스템 RAM 여유 최소값은 **모든 조합·모든 장수에서 10.1GB 이상** (서버 2 총 15GB, Hadoop·Kafka 상주 상태). 단일 프로세스 서빙 기준 RAM 은 제약이 아니다.
- 여유가 크므로 **동시 요청을 위한 다중 워커**(프로세스 복제, 워커당 ~1GB)도 RAM 상으로는 4 워커까지 무리 없음 — 단 CPU 4코어가 먼저 포화된다 (§5).

## 5. 동시 부하 테스트 (UX 판정)

파이프라인을 임시 HTTP 래퍼(`bench_serve.py`, 단일 uvicorn 워커)로 감싸고 Locust 로 M2 요청을 재현했다.
장수 분포: 1장 50% / 3장 35% / 10장 15%, 사용자당 요청 간 1~3초 대기, 각 단계 2분.

### 현행 v2 (`l_b`) — 요청 수(동시 사용자)별 p50 응답 (초)

| 동시 사용자 | 1장 요청 | 3장 요청 | 10장 요청 | 실패율 |
|---:|---:|---:|---:|---:|
| 1 | 1.1 | 3.1 | 9.9 | 0% |
| 3 | 1.9 | 6.2 | 26.0 | 0% |
| 5 | 3.9 | 12.0 | 43.0 | 0% |
| 10 | 9.0 | 28.0 | 94.0 | 0% |

- 단독(1명) 수치는 프로파일과 일치 — 래퍼 오버헤드는 무시 가능.
- **동시 3명부터 지연이 약 2배씩 증폭**된다. 4 vCPU를 단일 요청의 torch/YOLO 스레드가 이미 다 쓰기 때문에, 동시 요청은 순수하게 CPU 시간을 나눠 갖는다 (큐잉 지연).
- 실패(에러·타임아웃)는 없었다 — 느려질 뿐 죽지는 않는다.

### 권고 조합 (`s_s`) — 동일 시나리오

| 동시 사용자 | 1장 요청 | 3장 요청 | 10장 요청 | 실패율 | 부하 중 RAM 여유 최소 |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.4 | 1.1 | 3.6 | 0% | 10.4GB |
| 3 | 0.5 | 1.6 | 6.3 | 0% | 10.3GB |
| 5 | 0.9 | 2.6 | 9.1 | 0% | 10.2GB |
| 10 | 2.4 | 7.2 | 25.0 | 0% | 9.8GB |

- **동시 5명까지 1~3장 요청이 5초 안**에 든다 (현행 l_b 는 동시 3명에서 이미 3장 6.2초).
- 10장 요청은 단독으로도 3.6초라 동시성이 조금만 붙어도 5초를 넘는다 — 10장 상한을 쓰는 사용자에게는 어떤 구성에서도 동기 UX 를 약속할 수 없다.

### UX 판정

당시 판정 기준: 버튼 요청 → 결과 표시 평균 5초. 현재 개발 기준은 문서 상단의 비동기 SLO다.

1. **현행 v2 로는 동기 UX 가 성립하지 않는다.** 단독 사용자도 5장부터 5초를 넘고, 동시 3명이면 3장 요청조차 6초를 넘는다.
2. **`s_s` 전환 시 1~3장 요청은 동시 5명까지 동기 UX 가 성립한다.** 단 10장 요청은 단독 3.6초 → 동시 3명 6.3초로 경계선이다.
3. 동시 사용자가 늘면 어떤 조합이든 결국 CPU 4코어에서 밀린다. **UX 설계 권고**:
   - 요청 접수 즉시 응답(202) 후 **비동기 처리 + 완료 상태 폴링**을 기본 UX 로 설계하고,
   - 화면에는 진행 상태(탐지 중 → 유사도 계산 중)를 노출해 체감 대기를 줄인다.
   - 동기 응답을 유지하려면 s_s 전환 + 동시 처리 1~2건 제한(초과분 큐잉)이 전제되어야 한다.
4. RAM 여유는 부하 중에도 충분하므로 (아래 수치), 처리량 확장이 필요하면 스케일업(vCPU 증설)이나 워커 증설이 아니라 **비동기 큐가 먼저**다 — 워커를 늘려도 코어 수가 같으면 총 처리량은 그대로다.

## 6. 결론·후속 조치

1. **모델 사이즈**: `s_s` 전환 권고 (v3, 별도 이슈) — 사전 조건: vits14 재식별 정확도 검증. 보수안 `s_b`.
2. **탐지 배치화**: 현행 장당 루프를 배치 predict 로 바꾸면 l 유지 시에도 개선 여지 — 사이즈 전환과 독립적으로 검토 가능.
3. **서빙 형태**: 콜드 스타트(최대 4초) 때문에 요청당 프로세스 기동은 불가 — 상주 프로세스 필수.
4. **UX**: §5 판정 참조.
