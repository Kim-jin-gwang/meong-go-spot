## D1. 저장소 구조 — 모노레포

**결정:** `frontend/` + `backend/`를 하나의 저장소에서 관리한다.

**근거:**

- 6인 팀 규모에서 저장소 분리는 이슈·MR·CI 관리 지점만 늘린다.
- 하네스(AGENTS.md, 스킬, CI 설정)를 한 곳에만 유지하면 된다. 분리 시 하네스도 2벌.
- 기존 프로젝트(eye-dont-care)도 동일 구조였고 문제가 없었다.

**영향:** GitLab CI에서 FE/BE 변경 감지(`rules: changes`)로 필요한 잡만 실행하도록 구성한다.

---

## D2. 플랫폼 — GitLab

**결정:** 교육 과정에서 제공하는 GitLab을 사용한다. (환경 제약으로 사실상 확정)

**근거·교훈:** 기존 하네스의 `.github/` 계층(워크플로우 2개, 템플릿 9개, labels.json)은 GitLab에서 **한 번도 동작하지 않았다.** 이번에는 처음부터 GitLab 규격으로 만든다.

**영향:**

- 용어: PR → **MR** (문서 전체 치환)
- 템플릿 경로: `.gitlab/merge_request_templates/`, (이슈는 D5에 따라 Jira로)
- 워크플로우: `.gitlab-ci.yml`로 최초 구현 (재작성이 아니라 신규)
- 브랜치 보호: Protected branches + MR approval rules — "전원 approve" 규칙을 플랫폼 기능으로 강제 가능

## D3. 기술 스택

**결정:** 클라이언트 = **Android 앱** (Kotlin + Jetpack Compose), BE = Spring Boot.

> 2026-08-12 변경: FE를 Vue 3 → React로 변경 (팀 결정).
> 2026-08-25 변경: 주제 확정(멍고반점)과 함께 클라이언트를 웹 → **Android 앱**으로 변경 (팀 결정).
> React frontend/는 제거. 검사 체계는 ktlint + unit test로 대체하되 `npm run check` 계약은 유지.
> 지자체용 웹 대시보드가 실제로 필요해지는 시점에 웹 클라이언트 재도입을 재검토한다.

| 항목 | 확정값 | 비고 |
|---|---|---|
| 패키지 매니저 | **npm** | `package-lock.json` 커밋 필수 |
| Java 실행 기준 | **백엔드 Java 21 (LTS)** | 2026-08-12 변경 (25→21, 팀 표준에 맞춤). Spring Boot 3.2+ / 4.x에서 지원. Jenkins·GitLab CI 러너의 JDK도 21로 통일 |
| Android JVM 기준 | **JVM 17** | Android 앱의 Java/Kotlin 바이트코드 기준 |

**영향:** 기존 code-convention.md의 백엔드/프론트 섹션 대부분 재사용 가능. `docs/backend-*` 가이드 4종도 스택 동일 시 그대로 이식.

## D4. 브랜치 모델 — Git-Flow 축약형 (기존 유지)

**결정:** `main`(안정) + `dev`(통합) + 작업 브랜치(`feat/*`, `bugfix/*`, `refactor/*`, `docs/*`, `release/*`, `hotfix/*`).

**근거:**

- 팀이 이미 한 프로젝트를 이 모델로 완주했다 — 학습 비용 0.
- 기존 문서·스킬·템플릿 자산 전체가 이 모델 기준. 변경 시 이식 자산 절반이 무효.
- Trunk-based는 배포 자동화·feature flag가 전제라 현 단계에 부적합.

**기각한 대안:** Trunk-based Development — 팀 성숙도와 배포 인프라(서버 미발급 상태)가 전제 조건을 못 채움.

**영향:** 브랜치명 규칙은 D5에 따라 Jira 키를 포함하도록 확장: `feat/<JIRA-KEY>-<description>`.

---

## D5. 이슈 트래커 — Jira 일원화

**결정:** 계획·추적은 **Jira 단일**. GitLab Issues는 사용하지 않는다(비활성화 또는 미사용 명시). GitLab은 MR(코드 리뷰) 전용.

**근거:**

- 트래커 2개는 반드시 한쪽이 죽고 정보가 갈라진다. 원칙: **계획은 한 곳, 코드는 한 곳.**
- 교육 과정 프로젝트에서 Jira는 사실상 필수(평가 항목).
- 담당자의 Jira 자동화 역할과 일치.

**영향:**

- 기존 `.github/ISSUE_TEMPLATE/` 3종 → **폐기**, Jira 이슈 타입별 템플릿으로 재작성
- 기존 labels.json 30개 → **대부분 폐기**, Jira 필드로 매핑:
  `type/*`→이슈 타입, `priority/*`→Priority, `status/*`→워크플로우 상태, `area/*`→Component, `level/*`→포인트/커스텀 필드
- GitLab-Jira 연동 설정: 브랜치명·커밋·MR에 Jira 키(`PROJ-123`) 포함 → 티켓에 자동 연결
- Jira 자동화 4계층 로드맵: L0(내장 Automation) → L1(키 규칙) → L2(MCP 읽기) → L3(이벤트 쓰기, dry-run 먼저)

## D6. CI/CD 역할 분담 — GitLab CI(게이트) + Jenkins(배포)

**결정:**

| 도구 | 역할 | 상태 |
|---|---|---|
| **GitLab CI** (`.gitlab-ci.yml`) | MR 게이트: lint + typecheck + test (+ AI 리뷰) | **신규 구현** |
| **Jenkins** | 배포: build → deploy → health check → Mattermost 알림 | 기존 Jenkinsfile 재사용 + **Test 스테이지 추가** |

**근거·교훈:**

- 기존 프로젝트의 유일한 실동작 CI는 Jenkins였고, **lint/test 게이트는 존재한 적이 없다.** 이번 프로젝트의 최우선 신규 자산이 MR 게이트다.
- Gemini AI 리뷰는 GitHub Actions로 작성되어 한 번도 실행되지 않았다 → GitLab CI 잡으로 최초 구현. **non-blocking**(실패해도 머지를 막지 않음) 원칙 유지.
- GitLab CI만으로 배포까지 가능하지만, 교육 과정 인프라 관례와 기존 Jenkinsfile 자산(Mattermost 알림 포함)을 고려해 Jenkins 유지.

**영향:** MR 게이트는 required로 등록하고 3분 이내 피드백을 목표로 캐시를 필수 구성한다.

## D7. 배포 대상 — 서버 발급 후 확정 (열린 결정)

**결정:** 서버 발급 전까지 배포 구성은 보류하되, 다음을 전제로 준비한다.

- Docker Compose 기반 (`compose.dev.yml` / `compose.prod.yml` — 기존 자산 재사용)
- 시크릿은 Jenkins credential로 주입, `.env` 커밋 금지
- 롤백 경로(이전 이미지 태그 유지) 포함

**재검토 시점:** 서버 발급 시. 이 문서에 D7을 갱신한다.

---

## D8. 컨벤션 이식 방침

**결정:** 기존 컨벤션의 **내용은 동결**(재작성 금지), 이식 시 다음만 수행한다.

1. 모순 10건 청소 (컨벤션 통합본 부록 A 목록 기준)
2. PR→MR 용어 치환, GitHub 전용 서술 제거
3. 자동 검증 가능한 규칙을 강제 장치로 하강: commitlint(커밋 형식), CI 정규식(브랜치명), Protected branches(MR 대상), CI test — 부록 B의 ❌ 항목
4. 강제 장치가 생긴 규칙은 문서에서 상세 서술 축소 (설정 파일이 곧 문서)

**확정 3건:**

- [x] **dev 동기화: merge 단일** — 모든 브랜치에서 `git merge dev`로 통일. rebase·force push를 워크플로우에서 제거해 히스토리 사고(잘못된 force push, 커밋 유실) 가능성을 차단. 단순한 규칙이 6인 팀에 안전하다. → 커밋 전략 문서의 rebase/`--force-with-lease` 절은 이식 시 "사용하지 않음"으로 정리
- [x] **Gitmoji: 사용 금지** — commitlint가 강제하는 Conventional Commits만 사용. 도구 없는 규칙은 만들지 않는다. → 커밋 전략 문서의 Gitmoji 절(매핑표 포함) 전체 삭제
- [x] **API 버전: `/api/v1`** — 모든 API URL은 `/api/v1` prefix. `VITE_API_BASE_URL=/api/v1`로 프론트 설정 통일. 백엔드 가이드 문서의 `/api/coupons` 예시는 이식 시 `/api/v1/coupons`로 수정
