# 프로젝트 인프라 구축 순서 체크리스트

> 하네스 · CI/CD · 컨벤션 · 배포를 어떤 순서로 세울 것인가
> 원칙: **돌아가는 것 → 자동 검증 → 규칙 → 에이전트 → 문서**

---

## 왜 이 순서인가

의존성이 한 방향입니다.

```
검증 대상이 없으면 ─▶ 검증기를 못 만든다
검증기가 없으면    ─▶ 규칙은 장식이다
규칙이 없으면      ─▶ 에이전트는 지어낸다
```

흔히 쓰는 "컨벤션 문서 → 브랜치 전략 → 템플릿 → CI → 배포" 순서는 이 방향을 거스릅니다.
문서가 코드를 앞서면 반드시 어긋납니다.

---

## Stage 0 — 결정 (반나절)

코드 한 줄 쓰기 전에 정하고, **한 페이지 ADR로만** 기록합니다. (규칙 문서가 아니라 결정 기록)

- [ ] 저장소 구조 — 모노레포 / 분리
- [ ] **플랫폼 확정 — GitHub / GitLab** ← Stage 3·5의 구현이 통째로 달라짐
- [ ] 스택 — 언어, 프레임워크, 빌드툴, 패키지 매니저 (버전까지)
- [ ] 브랜치 모델 — git flow 축약형 / trunk-based (문서 말고 **결정만**)
- [ ] 이슈 트래커 — GitHub Issues / Jira / GitLab Issues
- [ ] CI 도구와 역할 분담 — Actions는 PR 게이트, Jenkins는 배포 (겹치지 않게)
- [ ] 배포 대상 — 서버, 컨테이너 여부, 도메인/포트

---

## Stage 1 — 레포 뼈대 (Day 1)

- [ ] **`.gitignore` · `.gitattributes` · `.editorconfig`** ← 반드시 첫 커밋
- [ ] 프론트/백 스캐폴딩 — "Hello World"가 로컬에서 뜬다
- [ ] `main`, `dev` 브랜치 생성
- [ ] `main` 직접 push 금지 설정

> **왜 이 3개 파일이 맨 앞인가:** 나중에 넣으면 전체 파일의 개행·공백이 한꺼번에 바뀌어
> diff가 폭발합니다. **비용이 시간에 비례해 커지는 유일한 항목**이라 맨 앞입니다.

**체크포인트:** 새 팀원이 `git clone` 후 한 명령으로 로컬 실행 가능

---

## Stage 2 — 단일 검증 명령 (Day 2~3) ★ 하네스의 진짜 시작점

- [ ] 포매터 설치·설정 커밋 (Prettier / Spotless)
- [ ] 린터 설치·설정 커밋 (ESLint / Checkstyle · ktlint)
- [ ] 타입체커 (vue-tsc / tsc)
- [ ] 테스트 러너 + **스모크 테스트 1개**
- [ ] **`make check` = lint + typecheck + test** 하나로 통일
- [ ] **`make fix` = 자동 수정 가능한 것 전부**
- [ ] Windows 팀이면 Makefile 대신 `npm run check` 또는 `just`

> **린터 설정 파일 자체가 컨벤션 문서보다 강력한 컨벤션입니다.**
> "들여쓰기 2칸"을 문서에 쓰는 대신 Prettier 설정에 박으면 논쟁이 끝납니다.

**체크포인트:** 아무 팀원이나 `make check` → 동일한 결과

---

## Stage 3 — CI 게이트 (Day 3~4) ★ 하네스의 척추

- [ ] PR 트리거로 `make check` 실행하는 워크플로우
- [ ] **required status check 등록** + `main`/`dev` 브랜치 보호
- [ ] **의존성 캐시 설정** (gradle / npm)
- [ ] 목표: PR 피드백 **3분 이내**

> 3분을 넘기면 팀이 CI를 미워하고 우회하기 시작합니다. 캐시는 선택이 아닙니다.

**체크포인트:** 일부러 린트를 깨뜨린 PR → 머지 버튼이 비활성화됨

> **여기까지가 최소 생존 세트입니다.** 시간이 없으면 Stage 0~3만 해도 하네스의 70%.

---

## Stage 4 — 로컬 훅 (Day 4)

- [ ] `lefthook` 설치 (Windows 팀이면 husky보다 안전)
- [ ] pre-commit: **변경된 파일만** format + lint
- [ ] commit-msg: `commitlint` (Conventional Commits 강제)
- [ ] 목표: **5초 이내**

> **원칙: 훅은 CI의 축소판이고, CI보다 빨라야 합니다.**
> 느리면 `--no-verify`로 우회당합니다. 전체 파일 검사는 금물.
>
> **왜 CI보다 뒤인가:** 훅은 우회 가능합니다. CI가 최종 게이트로 먼저 서 있어야
> 훅이 "빠른 피드백" 역할을 할 수 있습니다. 순서가 반대면 훅만 믿고 CI를 안 만듭니다.

---

## Stage 5 — 협업 규약 (Week 2) — 여기서 처음 "문서"가 등장

**각 규약은 반드시 `강제 장치 → 문서` 순으로 짝지어 만듭니다.**

| 규약 | 강제 장치 | 문서 |
|---|---|---|
| 코드 스타일 | Prettier · Spotless 설정 | **불필요** (설정이 곧 문서) |
| 커밋 형식 | commitlint (훅 + CI) | `commit-strategy.md` |
| 브랜치명 | CI 정규식 검사 잡 | `branch-strategy.md` |
| PR 대상 브랜치 | 브랜치 보호 규칙 | 〃 |
| 라벨 | `labels.json` + sync (**dry-run 포함**) | `label-strategy.md` |
| 리뷰어 지정 | `CODEOWNERS` | `CONTRIBUTING.md` |
| 이슈/PR 형식 | 템플릿 파일 | 템플릿 가이드 |

- [ ] 강제 장치 칸이 **빈 규칙은 쓰지 않는다** (다음 스테이지로 미루거나 폐기)
- [ ] 이슈 템플릿 · PR 템플릿
- [ ] `CODEOWNERS`
- [ ] `.env.example` — **실제 키 목록을 채워서** 커밋

---

## Stage 6 — 에이전트 하네스 (Week 2~3)

이제 규칙이 파일로 존재하므로 에이전트가 참조할 대상이 생겼습니다.

- [ ] `AGENTS.md` (원본) — **300줄 이내**
  - 프로젝트 개요 / 실행·검증 명령 / 절대 금지 / 문서 라우팅
  - [ ] **"커밋 전 `make check` 실행"** ← Stage 2의 명령을 여기서 회수
- [ ] `CLAUDE.md` — `@AGENTS.md` import + Claude 전용 보강만
- [ ] Antigravity 대응 (`AGENTS.md` 그대로 읽힘, 필요시 `.agent/rules/`)
- [ ] 스킬: `.ai/skills/` 원본 + 툴별 포인터 스텁
- [ ] MCP 서버 설정 (있다면, 생성 스크립트로 3툴 동시 배포)

> **Stage 5 없이 여기를 하면 에이전트가 규칙을 지어냅니다.**

---

## Stage 7 — AI 코드 리뷰 (Week 3)

- [ ] PR AI 리뷰 워크플로우
- [ ] **반드시 non-blocking** — API 실패나 리뷰 결과가 머지를 막지 않게
- [ ] `docs/` 컨텍스트 주입 + 문서 경로 인용 요구
- [ ] 마커 기반 코멘트 **업데이트** (커밋마다 새 코멘트 쌓임 방지)
- [ ] `concurrency` + `cancel-in-progress`
- [ ] 컨텍스트 상한 설정 (파일 수 / 문자 수)
- [ ] private repo면 **외부 전송 사실을 팀과 합의**

> AI 리뷰는 추론적 컨트롤이라 결정론적 게이트를 대체하지 못합니다.
> Stage 3 없이 이것만 있으면 "리뷰는 지적하는데 아무도 안 고침"이 됩니다.

---

## Stage 8 — 배포 (Week 3~4)

- [ ] `Dockerfile.dev` / `Dockerfile.prod`
- [ ] `compose.dev.yml` / `compose.prod.yml`
- [ ] 시크릿을 CI/Jenkins credential로 주입 (`.env`는 절대 커밋 금지)
- [ ] Jenkins 파이프라인:

```
Checkout → Validate → Test → Build → Deploy → Health check → 알림
                       ▲                        ▲
                   반드시 포함              반드시 포함
```

- [ ] **롤백 경로** — 이전 이미지 태그 유지, 되돌리는 명령을 문서화
- [ ] 배포 알림 (Mattermost / Discord webhook)
- [ ] 알림 실패가 배포 결과를 실패로 만들지 않게 처리

**GitHub Actions vs Jenkins 역할 분담**

| | 역할 | 이유 |
|---|---|---|
| Actions | PR 게이트 (빠른 검증) | 클라우드 러너, 설정 쉬움, PR 연동 |
| Jenkins | 배포 | 서버 접근 필요 |

Jenkins의 Test 스테이지는 **배포 직전 최종 확인**용이지 PR 게이트 대용이 아닙니다.

---

## Stage 9 — 이슈 트래커 자동화 (Week 4~)

- [ ] L0: 트래커 내장 Automation (PR 열림 → In Review, 머지 → Done)
- [ ] L1: 브랜치·커밋에 이슈 키 규칙 (`feat/PROJ-123-xxx`)
- [ ] L2: MCP 읽기 — 에이전트가 티켓 컨텍스트 활용
- [ ] L3: 이벤트 기반 쓰기 (**dry-run 먼저**, 봇 계정 분리)

---

## Stage 10 — 진화 루프 (상시)

- [ ] 같은 리뷰 코멘트 2회 이상 → 린트 룰 또는 `AGENTS.md`로 승격
- [ ] 격주 15분 하네스 회고 — 추가된 규칙 리뷰, **죽은 규칙 삭제**
- [ ] 지표 추적: CI 첫 시도 통과율 / PR 리뷰 반려 횟수 / `AGENTS.md` 라인 수

---

## 흔한 잘못된 순서 5가지

| 실수 | 결과 |
|---|---|
| 컨벤션 문서부터 쓰기 | 강제 장치 없는 장식. 문서와 실제가 어긋남 |
| 캐시 없이 CI 시작 | 빌드 5분 → 팀이 CI를 우회 |
| 배포부터 구축 | 배포는 되는데 품질 게이트가 영영 안 생김 |
| `AGENTS.md`를 맨 처음 쓰기 | 참조할 규칙이 없어 일반론만 담김 |
| 훅을 CI보다 먼저 | `--no-verify`로 무력화, CI는 안 만들게 됨 |

## 한 장 요약

```
Stage 0  결정 ─────────────────── 반나절
Stage 1  레포 뼈대 + 무시파일 ──── Day 1
Stage 2  make check ───────────── Day 2~3   ★ 하네스 시작
Stage 3  CI 게이트 ────────────── Day 3~4   ★ 척추 / 최소 생존선
Stage 4  로컬 훅 ──────────────── Day 4
Stage 5  협업 규약 + 문서 ─────── Week 2
Stage 6  에이전트 하네스 ──────── Week 2~3
Stage 7  AI 리뷰 ──────────────── Week 3
Stage 8  배포 파이프라인 ──────── Week 3~4
Stage 9  이슈 트래커 자동화 ───── Week 4~
Stage 10 진화 루프 ────────────── 상시
```
