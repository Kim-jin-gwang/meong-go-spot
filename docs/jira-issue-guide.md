## 이전 프로젝트 라벨 체계와의 매핑

이전 프로젝트의 GitHub 라벨 30종은 **폐기**하고 Jira 필드로 대체합니다.

| 기존 (GitHub 라벨) | Jira 대응 |
|---|---|
| `type/*` 8종 | **Issue Type** (Bug / Story / Task) |
| `priority/*` 3종 | **Priority** 필드 (High / Medium / Low) |
| `status/*` 5종 | **워크플로우 상태** (해야 할 일 / 진행 중 / 완료) |
| `area/*` 5종 | **Component** (BE / FE / INFRA) |
| `level/*` 3종 | **Story Point** |
| `needs/*` 3종 | 라벨 유지 또는 워크플로우 상태 |

> Jira 필드·워크플로우는 관리자 UI에서 관리되므로 코드화할 수 없습니다.
> 변경 시 이 문서를 갱신하는 것이 유일한 기록입니다.

## 이슈 작성 규칙

- 제목에 `[BUG]`, `[FEAT]` 같은 **대괄호 prefix를 사용하지 않습니다** — 분류는 Issue Type 필드가 담당합니다
- 재현 경로 / 기대 결과 / 현재 결과 / 영향 범위를 **구체적으로**
- 확인되지 않은 재현 방법·버전은 지어내지 말고 `확인 필요` 표시
- 티켓 연결이 필요하면 커밋·MR **본문**에 Jira 키(`#123`)를 적는다 (선택 — 브랜치명에는 넣지 않음)

## 이슈 타입별 Description 템플릿

Jira 이슈 생성 시 아래 템플릿을 Description에 붙여넣습니다.
(Jira 관리자 권한이 있으면 이슈 타입별 Default Description으로 등록)

### 버그 (Bug)

```text
## 문제 상황
-

## 재현 경로
1.

## 기대 결과
-

## 현재 결과
-

## 영향 범위
-

## 환경 (브라우저·OS·버전 — 미확인이면 "확인 필요")
-
```

### 기능 (Story)

```text
## 배경 / 필요한 이유
-

## 제안 내용
-

## 완료 조건 (Definition of Done)
- [ ]

## 영향 범위
-
```

### 리팩토링 (Task)

```text
## 현재 구조의 문제
-

## 개선 방향
-

## 동작 변경 여부
- 없음 (기존 테스트 전부 통과가 완료 조건)

## 영향 범위
-
```

## Triage 흐름

```text
1. 새 이슈 확인 (To Do)
2. 내용이 충분한지 검토 — 부족하면 작성자에게 질문 코멘트
3. Issue Type 확인
4. Component 지정
5. Priority 지정
6. 담당자 배정 → 스프린트/보드 배치
```

## 이슈 생성 방식 (2026-08-31 팀 결정)

**이슈는 원칙적으로 매주 월요일 팀 회의에서 팀원이 Jira 보드에 직접 생성·배정한다.** 이슈 생성 자동화(`draft-issue` 스킬, `scripts/jira-issue.mjs`)는 이 결정으로 **폐기**했다.

예외 (2026-09-01 개정): **본인 담당 이슈는 본인 판단으로 회의 밖에서도 생성할 수 있고**, 그 경우
AI 에이전트에게 지시해 API로 생성·상태 전환하는 것을 허용한다 (작성자·담당자=지시자 계정).
에이전트가 지시 없이 선제 생성하거나 타인 담당 이슈를 만드는 것은 여전히 금지.

- 스프린트 배정도 회의에서 함께 결정한다 (스프린트 필드가 비면 Jira는 백로그에 둔다)
- 하위 작업은 부모의 스프린트를 상속한다
- **브랜치명에는 이슈 번호를 넣지 않는다** ([branch-strategy.md](branch-strategy.md)). 티켓 연결이 필요하면 커밋 본문이나 MR 본문에 키를 적는다 (선택)

## 이슈 완료 처리 — 자동 전환의 발동 시점 (실측 2026-08-24)

GitLab의 Jira 자동 전환(`Closes 키`)은 해당 커밋이 **기본 브랜치(main)에 도달할 때** 발동한다.
우리 흐름은 MR→dev이므로, dev 병합 시점이 아니라 **다음 dev→main 동기화(릴리즈) 때** 완료로 넘어간다.

운영 규칙:

- MR 본문에는 `Closes #<번호>`를 기본으로 쓴다 (릴리즈 때 자동 완료되는 안전망)
- **dev 병합 직후의 완료 처리는 보드에서 직접** (카드를 "완료"로 드래그) — 자동 전환을 기다리지 않는다

| 단계 | 내용 | 상태 |

| L0 | GitLab Jira 연동의 자동 전환 (Move to Done) | ✅ 설정됨 — **단, 아래 발동 시점 주의** |
| L1 | 브랜치·커밋에 Jira 키 규칙 | ❌ 폐기 (2026-08-31) — 브랜치명에 키를 넣지 않음, 커밋·MR 본문 키는 선택 |
