# 게시물 날짜·정확한 위치 공개 정책

## 1. 목적과 범위

이 문서는 사용자 게시물 등록(P3)·메타데이터 수정(P4)·게시물 상세(P2)에 적용하는
`eventDate`와 정확한 위치 공개 계약의 단일 상세 기준이다. API 요약 계약은
[API 명세](api-spec.md)의 OD-07·OD-08·OD-09와 P2~P4를 따르며, 서로 다르면 이 문서의
상세 기준에 맞춰 함께 수정한다.

날짜 제한은 사용자가 직접 등록하는 `USER_POST`에 적용한다. 보호센터 공공데이터의 날짜는
수집 원천 계약에 따라 적재하므로 이 정책의 사용자 입력 검증 대상이 아니다.

## 2. 확정 요약

| 항목 | 정책 |
| --- | --- |
| 사용자 사건 날짜 | 서버의 `Asia/Seoul` 기준 오늘까지 허용, 내일부터 거부 |
| 미래 날짜 오류 | `400 COMMON-001`, `data.fieldErrors.eventDate`로 안내 |
| 공개 지역 | 검색은 5자리 `regionCode`, 표시는 코드에서 만든 시·군·구 및 선택 읍·면·동 `publicLocation` |
| 정확한 위치 | 위치별 `exactLocationVisible`, Android 기본값 `false` |
| 정확한 위치 공개 범위 | `ACTIVE` 사용자 게시물의 로그인 상세에서만 표시 |
| 작성자 관리 | 자신의 저장된 정확한 위치와 공개 상태 확인, 좌표는 제외 |
| 항상 비공개 | 비로그인 화면(비로그인 상세 포함), 목록, 검색, 후보 요약, 위도·경도 좌표 |
| 현재 안내 버전 | `exact-location-v1` |
| 버전 오류 | 오래되거나 알 수 없는 버전은 `409 POST-007` |
| Android | 위치별 공개 스위치와 `OFF -> ON` 확인, 자택 대신 랜드마크 입력 권장 |

## 3. 사건 날짜 검증

### 3.1 서버 기준

- P3의 `eventDate`는 필수 `YYYY-MM-DD`이고 P4에서 제공하면 같은 규칙을 적용한다.
- 서버가 요청을 검증하는 순간의 `Asia/Seoul` 달력 날짜를 `today`로 계산한다.
- `eventDate <= today`는 허용하고 `eventDate > today`는 거부한다.
- 애플리케이션 서버의 시스템 기본 시간대에 의존하지 않고 명시적인 `Clock`과
  `ZoneId.of("Asia/Seoul")`을 사용한다.
- `eventTime`은 선택 입력이며 이 정책에서는 날짜와 합쳐 미래 시각인지 추가 비교하지 않는다.
  형식 검증만 적용한다.
- 공공데이터 수집·정정에는 이 사용자 입력 상한을 적용하지 않는다.

`eventDate`가 미래이면 `400 COMMON-001`을 반환하고 `data.fieldErrors`에 다음처럼 안전한
필드 오류를 포함한다.

~~~json
{
  "code": "COMMON-001",
  "message": "요청 값이 올바르지 않습니다.",
  "data": {
    "fieldErrors": [
      {
        "field": "eventDate",
        "reason": "사건 날짜는 오늘 이후일 수 없습니다."
      }
    ]
  }
}
~~~

### 3.2 Android 선검증

- 날짜 선택기의 최대 날짜는 기기의 한국 시간 기준 오늘로 제한한다.
- 직접 입력이나 복원된 상태에도 같은 선검증을 적용한다.
- 기기 시각은 조작되거나 서버와 다를 수 있으므로 서버 검증이 최종 기준이다.
- 서버가 미래 날짜를 거부하면 사진과 나머지 유효 입력을 화면 수명 안에서 보존하고 날짜
  입력에 오류를 표시한다.

## 4. 위치별 공개 모델

### 4.1 공개 수준

위치 한 건은 공개 지역, 정확한 위치, 내부 좌표를 분리한다.

| 데이터 | 저장·사용 | 외부 표시 |
| --- | --- | --- |
| `regionCode`, `emdCode` | 5자리 시·군·구 코드와 선택 10자리 읍·면·동 코드 | 목록 지역 검색은 `EVENT.regionCode` 정확 일치. 상세 수정 복원에 코드 반환 |
| `publicLocation` | 서버가 행정구역 코드에서 만든 표시값 | 목록·후보·상세에 표시. 요약은 `EVENT`만 사용 |
| `exactLocation` | AES-256-GCM으로 저장하는 사용자 입력 상세 위치 | 다른 회원에게는 아래 공개 조건을 만족할 때만 표시. 작성자는 관리용 상세에서 자신의 저장값 확인 |
| `latitude`, `longitude` | 민감정보로 분류한 내부 시공간 매칭 값 | 어떤 API 응답·로그·metric label에도 표시하지 않음 |

Android는 자유 입력 지역명이 아니라 기준 데이터에서 `regionCode`와 선택 `emdCode`를 고른다.
서버는 코드 형식, 지원 여부와 상하위 소속을 검증하고 코드에서 `publicLocation`을 생성한다.
기준 데이터는 배포에 포함한 버전 고정 CSV와 SHA-256 checksum으로 관리한다. 파일·버전·checksum
불일치는 위치 쓰기 readiness 실패이며, 폐지 코드는 신규 쓰기에서 거부하되 기존 게시물은 저장된
표시값을 명시적 migration 전까지 유지한다.
공공데이터도 같은 기준 데이터로 정규화한다. 코드 매핑 실패를 임의 지역이나 문자열 검색으로
대체하지 않는다. `exactLocation`은 NFC·앞뒤 공백 제거 후 1~200 Unicode 코드 포인트이며
제어·형식 문자를 허용하지 않는다. 암호화 envelope와 좌표 보호 기준은
[백엔드 보안·운영 정책](backend-security-operations-policy.md)을 따른다.

정확한 위치를 다른 회원에게 공개하는 응답은 다음 조건을 모두 만족할 때만 반환한다.

1. `source=USER_POST`이고 게시물이 `ACTIVE`다.
2. 요청자가 로그인했다.
3. 해당 역할 위치의 `exactLocationVisible=true`다.
4. 같은 위치에 공백이 아닌 `exactLocation`이 저장돼 있다.
5. 같은 위치의 `disclosurePolicyVersion`이 서버의 현재 버전이고 동의 시각이 존재한다.

조건을 만족하지 않으면 다른 회원의 위치 객체에서 `exactLocation` 필드 자체를 생략한다.
비로그인 상세·목록, 로그인 목록·검색·유사 후보 요약에서는 공개 동의 여부와 관계없이 정확한
위치를 반환하지 않는다. 상세(P2)는 비로그인도 조회할 수 있지만 이때는 조건 2를 만족하지
못하므로 `exactLocation`이 없는 공개 응답만 받는다. 공공 보호동물은 위치 공개 동의 대상이 아니며 위치 행을 항상
`exactLocationVisible=false`로 유지한다.

작성자가 자신의 사용자 게시물 상세를 조회하면 수정 화면 복원을 위해 저장된 역할별
`exactLocation`과 `exactLocationVisible`을 반환한다. 이 소유자용 응답은 공개가 아니므로
`exactLocationVisible=false`와 `CLOSED` 게시물에도 적용할 수 있다. 좌표는 작성자에게도
반환하지 않고 `DELETED` 게시물은 조회할 수 없다.

### 4.2 역할별 독립 선택

- 사용자 `LOST`는 사건 위치 `EVENT` 공개 여부 한 개를 선택한다.
- 사용자 `SHELTERING`은 발견 장소 `EVENT`와 현재 보호 장소 `CURRENT`를 각각 선택한다.
- 한 역할의 변경은 다른 역할의 `exactLocationVisible`에 영향을 주지 않는다.
- 정확한 위치는 `exactLocationVisible=false`여도 내부 매칭을 위해 암호화 저장할 수 있다.
- `exactLocationVisible=true`이면 같은 역할에 공백이 아닌 `exactLocation`이 반드시 있어야 한다.
- 공개를 유지하면서 `exactLocation` 내용을 바꾸면 현재 안내 버전을 다시 확인한다.
- 서버의 공개 정책 버전이 올라가면 이전 버전 증빙이 있는 위치는 재확인 전까지 다른 회원에게
  공개하지 않는다. DB의 공개 flag를 자동으로 동의로 간주하지 않는다.
- 게시물을 종료하거나 삭제하면 이전 공개 선택과 관계없이 다른 사용자에게 정확한 위치를
  반환하지 않는다. 종료 게시물의 작성자 관리용 조회만 저장된 위치를 확인할 수 있다.

## 5. Android 표시와 확인

각 `EVENT`·`CURRENT` 입력 영역에 별도의 `정확한 위치 공개` 스위치를 두고 최초값은 `OFF`로
한다. `SHELTERING` 화면에서 두 스위치의 상태를 묶거나 복사하지 않는다.

공개 안내 문구는 다음을 기준으로 한다.

> 정확한 위치를 공개하면 로그인한 사용자가 게시물 상세에서 확인할 수 있습니다.
> 목록·검색·유사 후보에는 표시되지 않으며 위치 좌표는 공개되지 않습니다.
> 자택 주소 대신 주변 랜드마크를 입력해 주세요.

- `OFF -> ON` 전환 시 위 공개 대상과 범위를 확인하는 다이얼로그를 표시한다.
- 사용자가 확인해야만 스위치를 `ON`으로 바꾸고 현재 정책 버전을 요청에 넣는다.
- `ON -> OFF`는 추가 확인 없이 즉시 선택할 수 있고 P4 저장 성공 직후 비공개로 반영한다.
- 스위치는 색상만으로 상태를 표현하지 않고 텍스트·접근성 상태 설명을 함께 제공한다.
- 서버가 `POST-007`을 반환하면 입력을 보존하고 최신 앱으로 업데이트한 뒤 공개 내용을 다시
  확인하도록 안내한다.
- 작성자 관리 화면은 소유자 P2 응답의 `exactLocationVisible`로 각 스위치를 복원하고,
  비공개인 저장 위치도 다시 입력하게 하지 않도록 `exactLocation`을 채운다.

## 6. 공개 안내 버전

### 6.1 현재 값과 책임

현재 `disclosurePolicyVersion`은 `exact-location-v1`이다. 이 문서가 안내 내용과 버전의
사람이 읽는 원본이며, Spring Boot가 현재 허용 버전을 최종 검증한다. Android의 문자열과
요청 버전은 같은 변경에서 함께 갱신한다.

MVP에서는 별도의 정책 조회 API나 원격 설정을 두지 않는다. 버전 변경은 Android·Backend·이
문서를 한 MR에서 바꾸고 함께 배포한다. 이전 앱이 현재 버전이 아닌 값을 보내면 서버는 요청을
수락하지 않는다.

### 6.2 버전을 올리는 경우

다음 의미가 달라지면 `exact-location-v2`처럼 버전을 올린다.

- 정확한 위치를 볼 수 있는 사용자 범위
- 정확한 위치가 표시되는 화면이나 기능 범위
- 위치를 저장·공개하는 목적
- 좌표를 포함해 새로 공개되는 데이터 종류
- 사용자가 공개 여부를 선택하거나 철회하는 방식

뜻이 바뀌지 않는 오탈자, 조사, 줄바꿈과 표현 정리는 버전을 올리지 않는다.

### 6.3 P3·P4 검증

- P3은 `exactLocationVisible=true`인 각 위치 객체에
  `disclosurePolicyVersion=exact-location-v1`을 보낸다. 비공개 위치에는 버전이 필요하지 않다.
- P4에서 위치의 공개가 `false -> true`가 되거나 공개를 유지한 채 `exactLocation`을 바꾸면
  같은 위치 객체의 현재 `disclosurePolicyVersion`이 필수다.
- P4의 `true -> false`, 정확한 위치를 바꾸지 않는 날짜·공개 지역·특징 등 다른 필드만 수정하는
  요청에는 버전이 필수가 아니다.
- 요청에 버전이 포함되면 현재 값과 정확히 일치해야 한다. 누락이 허용되지 않는 요청에서
  빠졌거나 값이 다르면 `POST-007`이다.

## 7. 저장과 감사 증빙

- P3 성공 시 공개가 true인 각 `animal_case_location` 행의 `disclosure_policy_version`에 현재
  버전, `disclosure_consented_at`에 서버 처리 시각을 저장한다. 비공개 행의 두 값은 `NULL`이다.
- P4의 `OFF -> ON` 또는 공개 유지 중 정확한 위치 변경 성공 시 해당 위치 행의 두 값을 현재
  버전과 새 처리 시각으로 함께 갱신한다.
- `ON -> OFF`에서는 위치 행의 공개 여부만 바꾸고 마지막 공개 확인 버전·시각은 감사 증빙으로
  보존한다.
- `EVENT`·`CURRENT`의 실제 공개 상태는 각각
  `animal_case_location.exact_location_visible`이 최종 기준이다.
- 버전과 확인 시각은 역할별 공개 상태 자체가 아니라 해당 정확한 위치에 대해 사용자가 마지막으로
  확인한 안내를 증빙한다.
- 정책 버전, 공개 여부와 처리 시각은 기록할 수 있지만 정확한 위치 평문·좌표는 애플리케이션
  로그와 오류 응답에 남기지 않는다.

## 8. 오류 계약

| 상황 | HTTP | 코드 | Android 처리 |
| --- | ---: | --- | --- |
| P3·P4의 미래 `eventDate` | 400 | `COMMON-001` | 날짜 입력 오류, 나머지 입력 보존 |
| `exactLocationVisible=true`인데 정확한 위치 없음 | 400 | `COMMON-001` | 같은 역할의 정확한 위치 입력 안내 |
| P3의 공개 위치 안내 버전 누락·불일치 | 409 | `POST-007` | 최신 앱·해당 위치 안내 확인 후 재시도 |
| P4 `OFF -> ON` 또는 공개 위치 내용 변경의 안내 버전 누락·불일치 | 409 | `POST-007` | 스위치 확인 상태를 되돌리고 안내 재확인 |

버전 불일치를 일반 필드 형식 오류와 구분해 Android가 입력을 버리지 않고 정책 재확인 동선을
제공할 수 있게 한다.

## 9. 필수 검증

- `Asia/Seoul` 자정 직전·직후에 어제·오늘·내일 날짜의 허용 경계를 고정 `Clock`으로 검사한다.
- P3과 P4가 같은 날짜 검증기를 사용하고 미래 날짜를 `COMMON-001`로 거부하는지 검사한다.
- Android 날짜 선택기·직접 입력이 미래 날짜를 막고 서버 오류 뒤 입력을 보존하는지 검사한다.
- P3에서 공개 true인 위치의 현재·누락·알 수 없는 안내 버전을 각각 성공·`POST-007`로 검사하고,
  모든 위치가 false면 버전 없이 등록되는지 검사한다.
- P4의 `false -> true`와 공개 유지 중 정확한 위치 변경은 현재 버전을 요구하고 `true -> false`는
  버전 없이 허용하는지 검사한다.
- 정책 버전을 올렸을 때 이전 버전 증빙 위치가 재확인 전까지 다른 회원 응답에서 사라지는지 검사한다.
- `LOST`의 `EVENT`, `SHELTERING`의 `EVENT`·`CURRENT` 공개 선택이 서로 독립적인지 검사한다.
- 비로그인 목록, 로그인 목록·검색·후보에 정확한 위치·좌표가 없는지 검사한다.
- 다른 회원의 로그인 상세는 활성 사용자 게시물에서 동의한 역할의 정확한 위치만 반환하는지
  검사한다.
- 작성자 상세는 공개 선택과 관계없이 저장된 정확한 위치와 스위치 상태를 반환하되 좌표는
  제외하고, 종료 게시물에도 같은 관리용 응답을 적용하는지 검사한다.
- 종료·삭제 게시물과 공공 보호동물에서 정확한 위치를 반환하지 않는지 검사한다.
- 응답·오류·로그에 비공개 정확한 위치 평문과 좌표가 없는지 검사한다.

## 10. 제외 범위

MVP에서는 미래 일정 예약 게시물, 정책 문구 조회 API, 원격 정책 설정, 이전 버전 동시 허용,
별도 동의 이력 테이블, 정확한 위치의 비로그인 공개와 좌표 공개를 제공하지 않는다. 역할별 마지막
동의 증빙만 위치 행에 유지한다.
